Simulating Sensors: LiDAR, Depth Cameras, and IMUs

Learning Objectives​

By the end of this chapter, you will be able to:

  • Explain why sensor simulation is critical for Physical AI development
  • Configure and simulate 2D and 3D LiDAR sensors in Gazebo
  • Set up RGB-D (depth camera) sensors with realistic parameters
  • Simulate IMU sensors for orientation and acceleration measurement
  • Add standard camera sensors with configurable resolution and field of view
  • Implement sensor noise models that approximate real-world sensor behavior
  • Use Gazebo sensor plugins to publish data to the simulation transport layer

Why Simulate Sensors?​

A robot without sensors is blind. In Physical AI, sensors are how the robot perceives the world -- they are the input pipeline for every perception, navigation, and manipulation algorithm.

Simulating sensors serves three purposes:

  1. Algorithm development: Develop and debug perception algorithms without needing real hardware
  2. Synthetic data generation: Generate labeled training data for computer vision and ML models (the ground truth is always known in simulation)
  3. Sim-to-real validation: Verify that your perception pipeline works before deploying to a physical robot
The Sim-to-Real Gap

Simulated sensors are approximations. Real cameras have lens distortion, rolling shutter artifacts, and auto-exposure. Real LiDAR has beam divergence and multi-path reflections. Noise models help bridge this gap, but always validate on real hardware before production deployment.

Sensor Fundamentals in Gazebo​

How Gazebo Sensors Work​

In Gazebo, sensors are attached to links in your robot model. Each sensor has:

  • A type (camera, lidar, imu, etc.)
  • A pose relative to the parent link
  • Parameters specific to the sensor type (resolution, range, FOV)
  • An optional noise model
  • An update rate (how often the sensor produces data)

The gz-sensors library computes sensor outputs each update cycle and publishes them via gz-transport topics.

General Sensor SDF Structure​

<link name="sensor_link">
  <sensor name="my_sensor" type="camera">
    <pose>0 0 0.1 0 0 0</pose>
    <update_rate>30</update_rate>
    <always_on>true</always_on>
    <visualize>true</visualize>
    <!-- Sensor-specific parameters -->
    <camera>
      <!-- ... -->
    </camera>
  </sensor>
</link>

LiDAR Simulation​

What is LiDAR?​

LiDAR (Light Detection and Ranging) uses laser pulses to measure distances. It produces a point cloud -- a set of 3D points representing the surfaces of objects around the sensor.

2D LiDAR (Planar Scanner)​

A 2D LiDAR scans in a single plane, producing a ring of distance measurements. Common in mobile robots for navigation and obstacle avoidance.

<link name="lidar_link">
  <pose>0 0 0.3 0 0 0</pose>
  <sensor name="lidar_2d" type="gpu_lidar">
    <pose>0 0 0 0 0 0</pose>
    <update_rate>10</update_rate>
    <always_on>true</always_on>
    <visualize>true</visualize>
    <ray>
      <scan>
        <horizontal>
          <samples>360</samples>
          <resolution>1.0</resolution>
          <min_angle>-3.14159</min_angle>
          <max_angle>3.14159</max_angle>
        </horizontal>
        <vertical>
          <samples>1</samples>
          <resolution>1.0</resolution>
          <min_angle>0</min_angle>
          <max_angle>0</max_angle>
        </vertical>
      </scan>
      <range>
        <min>0.1</min>
        <max>30.0</max>
        <resolution>0.01</resolution>
      </range>
      <noise>
        <type>gaussian</type>
        <mean>0.0</mean>
        <stddev>0.01</stddev>
      </noise>
    </ray>
  </sensor>
</link>

Key parameters explained:

  • samples: Number of laser beams per scan (360 = 1 degree resolution)
  • min_angle / max_angle: Scan range in radians (-pi to pi = full 360 degrees)
  • min / max range: Measurement distance bounds in meters
  • noise: Gaussian noise with mean 0 and standard deviation 0.01 meters (1 cm)

3D LiDAR (Multi-beam Scanner)​

A 3D LiDAR like the Velodyne VLP-16 uses multiple vertically stacked beams to produce a 3D point cloud:

<sensor name="lidar_3d" type="gpu_lidar">
  <pose>0 0 0.5 0 0 0</pose>
  <update_rate>10</update_rate>
  <always_on>true</always_on>
  <visualize>true</visualize>
  <ray>
    <scan>
      <horizontal>
        <samples>1800</samples>       <!-- 0.2 degree horizontal resolution -->
        <resolution>1.0</resolution>
        <min_angle>-3.14159</min_angle>
        <max_angle>3.14159</max_angle>
      </horizontal>
      <vertical>
        <samples>16</samples>          <!-- 16 vertical beams (VLP-16) -->
        <resolution>1.0</resolution>
        <min_angle>-0.2618</min_angle> <!-- -15 degrees -->
        <max_angle>0.2618</max_angle>  <!--  15 degrees -->
      </vertical>
    </scan>
    <range>
      <min>0.3</min>
      <max>100.0</max>
      <resolution>0.003</resolution>   <!-- 3mm range resolution -->
    </range>
    <noise>
      <type>gaussian</type>
      <mean>0.0</mean>
      <stddev>0.02</stddev>            <!-- 2cm noise -->
    </noise>
  </ray>
</sensor>
GPU vs CPU LiDAR

Use type="gpu_lidar" whenever possible. GPU-based ray casting is orders of magnitude faster than CPU-based, especially for 3D LiDAR with thousands of beams. This requires a GPU with OpenGL support.

Depth Camera (RGB-D) Simulation​

What is a Depth Camera?​

A depth camera produces two synchronized outputs:

  1. RGB image: Standard color image
  2. Depth image: Per-pixel distance to the nearest surface

Common depth cameras include the Intel RealSense D435 and Microsoft Azure Kinect.

Configuring a Depth Camera​

<link name="camera_link">
  <pose>0 0 0.4 0 0 0</pose>
  <sensor name="rgbd_camera" type="rgbd_camera">
    <pose>0 0 0 0 0 0</pose>
    <update_rate>30</update_rate>
    <always_on>true</always_on>
    <camera>
      <horizontal_fov>1.2112</horizontal_fov>  <!-- ~69 degrees (RealSense D435) -->
      <image>
        <width>640</width>
        <height>480</height>
        <format>R8G8B8</format>
      </image>
      <clip>
        <near>0.1</near>
        <far>10.0</far>
      </clip>
      <depth_camera>
        <clip>
          <near>0.1</near>
          <far>10.0</far>
        </clip>
      </depth_camera>
      <noise>
        <type>gaussian</type>
        <mean>0.0</mean>
        <stddev>0.007</stddev>
      </noise>
    </camera>
  </sensor>
</link>

Depth Camera Output​

The depth camera publishes several data streams:

  • /camera/image: RGB color image
  • /camera/depth_image: 32-bit float depth image (meters per pixel)
  • /camera/points: 3D point cloud (combined RGB + depth)
  • /camera/camera_info: Camera intrinsic parameters (focal length, principal point)

Simulating the Intel RealSense D435​

To match the real D435 specifications:

<camera>
  <!-- D435 RGB camera specs -->
  <horizontal_fov>1.2112</horizontal_fov>  <!-- 69.4 degrees -->
  <image>
    <width>1280</width>
    <height>720</height>
    <format>R8G8B8</format>
  </image>
  <clip>
    <near>0.105</near>   <!-- D435 minimum depth: 10.5 cm -->
    <far>10.0</far>       <!-- Useful range ~10m -->
  </clip>
  <depth_camera>
    <clip>
      <near>0.105</near>
      <far>10.0</far>
    </clip>
  </depth_camera>
</camera>

IMU (Inertial Measurement Unit) Simulation​

What is an IMU?​

An IMU measures:

  • Linear acceleration (accelerometer) -- in m/s^2
  • Angular velocity (gyroscope) -- in rad/s
  • Some IMUs also include a magnetometer (compass)

IMUs are critical for humanoid balance: they tell the robot which way is up and how fast it is rotating.

Configuring an IMU​

<link name="imu_link">
  <pose>0 0 0.5 0 0 0</pose>  <!-- Mounted on torso -->
  <sensor name="imu_sensor" type="imu">
    <pose>0 0 0 0 0 0</pose>
    <update_rate>200</update_rate>   <!-- 200 Hz typical for robotics IMUs -->
    <always_on>true</always_on>
    <imu>
      <angular_velocity>
        <x>
          <noise type="gaussian">
            <mean>0.0</mean>
            <stddev>0.0002</stddev>   <!-- rad/s -->
            <bias_mean>0.0000075</bias_mean>
            <bias_stddev>0.0000008</bias_stddev>
          </noise>
        </x>
        <y>
          <noise type="gaussian">
            <mean>0.0</mean>
            <stddev>0.0002</stddev>
            <bias_mean>0.0000075</bias_mean>
            <bias_stddev>0.0000008</bias_stddev>
          </noise>
        </y>
        <z>
          <noise type="gaussian">
            <mean>0.0</mean>
            <stddev>0.0002</stddev>
            <bias_mean>0.0000075</bias_mean>
            <bias_stddev>0.0000008</bias_stddev>
          </noise>
        </z>
      </angular_velocity>
      <linear_acceleration>
        <x>
          <noise type="gaussian">
            <mean>0.0</mean>
            <stddev>0.017</stddev>    <!-- m/s^2 -->
            <bias_mean>0.1</bias_mean>
            <bias_stddev>0.001</bias_stddev>
          </noise>
        </x>
        <y>
          <noise type="gaussian">
            <mean>0.0</mean>
            <stddev>0.017</stddev>
            <bias_mean>0.1</bias_mean>
            <bias_stddev>0.001</bias_stddev>
          </noise>
        </y>
        <z>
          <noise type="gaussian">
            <mean>0.0</mean>
            <stddev>0.017</stddev>
            <bias_mean>0.1</bias_mean>
            <bias_stddev>0.001</bias_stddev>
          </noise>
        </z>
      </linear_acceleration>
    </imu>
  </sensor>
</link>

IMU Noise Parameters Explained​

Real IMU sensors exhibit two types of noise:

  1. White noise (stddev): Random fluctuations each measurement cycle
  2. Bias (bias_mean, bias_stddev): A slowly drifting offset that accumulates over time
ParameterTypical ValueUnit
Gyro noise density0.0002rad/s/sqrt(Hz)
Gyro random walk0.0000075rad/s^2/sqrt(Hz)
Accel noise density0.017m/s^2/sqrt(Hz)
Accel random walk0.001m/s^3/sqrt(Hz)

These values approximate a mid-range MEMS IMU (like the Bosch BMI088 used in many drones and robots).

IMU Bias Drift

In the real world, IMU bias drifts over time. If you integrate angular velocity to estimate orientation, this drift accumulates and your estimate diverges. This is why real robots use sensor fusion (IMU + visual odometry + external references). Simulating bias helps you develop and test these fusion algorithms.

Standard Camera Sensors​

Basic RGB Camera​

<sensor name="camera" type="camera">
  <pose>0 0 0.5 0 0 0</pose>
  <update_rate>30</update_rate>
  <always_on>true</always_on>
  <visualize>true</visualize>
  <camera>
    <horizontal_fov>1.3962634</horizontal_fov>  <!-- 80 degrees -->
    <image>
      <width>1920</width>
      <height>1080</height>
      <format>R8G8B8</format>
    </image>
    <clip>
      <near>0.02</near>
      <far>300</far>
    </clip>
    <lens>
      <intrinsics>
        <fx>1108.5</fx>
        <fy>1108.5</fy>
        <cx>960.0</cx>
        <cy>540.0</cy>
        <s>0</s>
      </intrinsics>
    </lens>
    <noise>
      <type>gaussian</type>
      <mean>0.0</mean>
      <stddev>0.007</stddev>
    </noise>
  </camera>
</sensor>

Camera Intrinsics​

The <intrinsics> section defines the camera's internal parameters:

  • fx, fy: Focal length in pixels
  • cx, cy: Principal point (usually image center)
  • s: Skew coefficient (usually 0)

These parameters are essential for 3D reconstruction and computer vision algorithms. In simulation, you control them exactly -- in the real world, you must calibrate to determine them.

Relationship Between FOV and Focal Length​

The horizontal field of view and focal length are related by:

import math

width = 1920  # pixels
hfov = 1.3962634  # radians (80 degrees)

# Compute focal length from FOV and image width
fx = width / (2.0 * math.tan(hfov / 2.0))
print(f"Focal length: {fx:.1f} pixels")
# Output: Focal length: 1108.5 pixels

Sensor Noise Models​

Why Add Noise?​

Perfect sensors do not exist. If you develop algorithms with perfect sensor data in simulation, they will fail on real hardware. Noise models bridge the sim-to-real gap.

Gaussian Noise​

The most common noise model. Each measurement has random noise added:

measurement = true_value + N(mean, stddev)
<noise>
  <type>gaussian</type>
  <mean>0.0</mean>
  <stddev>0.01</stddev>
</noise>

Depth-Dependent Noise​

Real depth cameras have noise that increases with distance. While Gazebo does not natively support this, you can approximate it with a custom sensor plugin or post-process the depth image:

"""Add realistic depth-dependent noise to a simulated depth image."""

import numpy as np


def add_depth_noise(depth_image: np.ndarray, base_noise: float = 0.001,
                    depth_factor: float = 0.005) -> np.ndarray:
    """Add noise that scales with depth.
    
    Args:
        depth_image: HxW array of depth values in meters.
        base_noise: Baseline noise standard deviation (meters).
        depth_factor: Noise scaling factor per meter of depth.
    
    Returns:
        Noisy depth image.
    """
    noise_std = base_noise + depth_factor * depth_image
    noise = np.random.normal(0, noise_std)
    noisy_depth = depth_image + noise
    
    # Clamp to valid range
    noisy_depth = np.clip(noisy_depth, 0.1, 10.0)
    return noisy_depth

Complete Sensor-Equipped Robot Model​

Here is an SDF model that attaches all the sensors we have discussed to a simple robot base:

    <link name="base_link">

        <geometry><box><size>0.5 0.3 0.2</size></box></geometry>

Viewing Sensor Data​

In the Gazebo GUI​

  1. Click the hamburger menu (top-right)
  2. Select Image Display plugin for camera feeds
  3. Select Visualize Lidar to see LiDAR rays in the 3D scene
  4. Use the Topic Viewer to inspect raw data

Via Command Line​

# List sensor topics
gz topic --list

# View LiDAR data
gz topic --echo --topic /world/default/model/sensor_bot/link/lidar_link/sensor/lidar/scan

# View IMU data
gz topic --echo --topic /world/default/model/sensor_bot/link/base_link/sensor/imu/imu

# Save camera image
gz topic --echo --topic /world/default/model/sensor_bot/link/camera_link/sensor/rgbd/image \
  --num 1 > camera_frame.raw
